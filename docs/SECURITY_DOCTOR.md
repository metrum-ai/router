# Security posture checks

`metrum-ai-routerctl doctor --security` evaluates the local router configuration and can probe a running target without sending credentials.

```sh
metrum-ai-routerctl doctor --security --config config.yaml
metrum-ai-routerctl doctor --security --config config.yaml --format json --fail-on warn
metrum-ai-routerctl doctor --security --config config.yaml --target https://router.example
metrum-ai-routerctl doctor --security --config deployment.yaml --advisories ./engine-advisories.json
metrum-ai-routerctl doctor --security --config config.yaml --report-latest --router-url https://router.example --admin-key-file ./admin.key
```

The report uses `pass`, `warn`, `fail`, and informational `not checked` findings with safe summaries and fix guidance. `--fail-on fail` (the default) exits nonzero for failed checks; `--fail-on warn` also exits nonzero for warnings. `not checked` findings do not fail either threshold. JSON output uses the `metrum.ai/router-security-posture/v1` schema.

Configuration checks cover non-loopback serving TLS, provider key source and spend ceilings, admin exposure, disabled security reports, caller limits and token format/entropy metadata, development/test keys, active metrics authorization, sensitive-tagged model targets without PII filtering, and caller key age. Revoked and disabled callers are excluded from key checks. Keys older than 90 days fail; missing or future `callers[].token_issued_at` timestamps warn. Token generation and admin issue/rotation record the UTC RFC3339 timestamp. For manually managed keys, set the original issue time. Token values are never read; weak-key findings use `token_format_version` and `token_entropy_bits`. A warning for a missing spend ceiling is advisory because provider ceilings are optional. In database config mode, the command warns that DB-stored callers and key metadata were not checked.

`/metrics` stays on the serving port and requires a caller with `metrics_admin: true`; it is not moved to the admin listener in this release. Missing metrics authorization configuration warns with a supported caller setting. `--target` issues unauthenticated `GET /metrics` with a three-second deadline. A successful response fails the metrics authorization check; 401 and 403 pass; other statuses warn because access control is inconclusive. A network error or timeout fails the probe. Redirects are not followed. The command never sends credentials or reads response bodies. Plain HTTP is accepted only for loopback targets; use HTTPS remotely.

Engine image pins in the operator YAML are compared with the release advisory snapshot generated by the engine advisory gate. Pass `--advisories <file>` to use a specific snapshot. Otherwise, the command reads `engine-advisories.json` beside the release binary when present. The advisory check does not search for or execute source scripts and makes no network requests. `--target` and `--report-latest` are explicit network operations described above. If no snapshot is available, the finding is informational `not checked`, so offline `--fail-on warn` can pass.

### Reference configuration findings

The reference-config test checks `config.example.yaml`, the edge template, the deployment reference configs, and the Kubernetes router configs after replacing install-time placeholders with harmless test values. Expected warnings are limited to `serving-tls`, `provider-key-source`, `provider-spend-ceiling`, `security-reports`, `metrics-auth-config`, `caller-limits`, `caller-key-format`, `caller-key-environment`, `caller-key-age`, `engine-pin-advisories`, and `db-stored-callers`. These identify optional hardening settings, template credentials/metadata, or checks unavailable without the release snapshot or database. The `deploy/kubernetes/overlays/admin-plane/config.yaml` example also intentionally has `admin-listener` and `admin-plaintext` failures: that overlay documents a private Service and default-deny NetworkPolicy as its network boundary. The doctor evaluates the config alone and cannot verify Kubernetes network policy; deployments must preserve that boundary or configure listener TLS/mTLS.

`--report-latest` sends only the schema version, timestamp, aggregate outcome, and check identifiers/status/severity to `/admin/v1/reports/security/posture/latest`. It uses the existing admin key from `--admin-key-file`, `ROUTER_ADMIN_KEY`, or `ROUTER_ADMIN_KEY_FILE`; the key is never a flag value. Grant `admin:security_reports, write` only to the self-test operator. The router retains one latest summary in the usage database; details, fixes, target addresses, and credentials are excluded. Apply the checked-in usage database migrations before using this endpoint.

The command reads and validates configuration but does not modify it. Keep any JSON report in a protected location because it describes the deployment's security posture.
