# Four-expert routing comparison on 4× H200 (#426)

**Negative result, not parity:** on the fixed public 88-case cohort, the TP=4
baseline passed **56/88** strict checks and the routed experts **45/88**
(−11/88, or −12.5 percentage points). All 176 responses were HTTP 200.
The keyword classifier was correct on **37/88** cases; **42/88** were routed to
the expected provider. All 88 classifier decisions joined. Class and route
accuracy differ because five coding cases fell back to coding despite being
classified unknown. Misrouting is central to interpreting this comparison.

## Per-domain quality

| Cases | Baseline passed | Routed experts passed |
|---|---:|---:|
| Biomedical | 15/20 | 11/20 |
| Finance | 12/20 | 13/20 |
| Math | 6/20 | 1/20 |
| Coding | 15/20 | 13/20 |
| Out-of-domain fallback | 8/8 | 7/8 |
| **Total** | **56/88** | **45/88** |

For the 80 in-domain cases, the baseline passed 48 and routed experts 38.
Each of the same 88 case IDs was attempted once per arm. Paired outcomes were
five cases passed only by the routed arm, 16 only by the baseline, and 67
agreements. These are small, public, potentially contaminated samples; coding
is multiple-choice syntax, not execution of generated code.

## Routing and observed expert quality

| Observed routed arm | Strict passes | Cases |
|---|---:|---:|
| Expected provider selected | 26 | 42 |
| Wrong provider selected | 19 | 46 |
| Correct classifier label | 21 | 37 |
| Incorrect classifier label | 24 | 51 |

The expected-provider split includes coding fallback for eight out-of-domain
cases. Of the 46 wrong-provider cases, **16 biomedical, 15 finance and 15
math** fell back to coding. On correctly routed in-domain cases, biomedical
passed 2/4, finance 3/5, math 1/5 and coding 13/20; the out-of-domain fallback
passed 7/8. On misrouted cases, biomedical passed 9/16, finance 10/15 and math
0/15. These descriptive subsets differ in domain, difficulty and size, so they
do **not** establish a causal loss from misrouting or isolate intrinsic model
quality. The nonzero failure rate on correctly routed cases also shows that
perfect routing alone cannot be assumed to make this observed run perfect.

**No expert-oracle estimate is available offline.** Only the selected expert
was run for each case, and saved result records intentionally omit generated
text. The unselected experts' counterfactual outputs are unavailable. The
61/88 cases passed by either observed arm are a hindsight combination of the
baseline and chosen expert, **not** an expert-routing oracle or deployable
routing estimate. No additional GPU inference was used for this analysis.

## Throughput and timing

Closed-loop concurrency four and equal case counts do not establish a matched
arrival-rate workload. Both arms use the same loopback SSH-tunnel and router
arrangement. Each figure has 88 observations.

| Metric | TP=4 baseline | Routed experts |
|---|---:|---:|
| Elapsed seconds | 10.84 | 13.06 |
| Completed responses/s | 8.12 | 6.74 |
| Strict passes/s | 5.17 | 3.44 |
| End-to-end p50 / p99 ms | 396 / 937 | 344 / 1,515 |
| Streaming TTFT p50 / p99 ms | 327 / 900 | 304 / 909 |

Classifier telemetry recorded policy duration p50 0 ms and p99 1 ms; these
are recorded values, not sub-millisecond precision measurements. No generated
code was executed. Model capabilities, language/domain mismatches, serving
architecture and small sample composition all confound interpretation.

## Reproducibility and operations

The fixed public suite is SHA-256
`894fdd2eb4989f75ad428a40e519200de8f066e6b0bc74db69501a060f52ee77`;
its public source and frozen model revisions are in the preregistered plan.
The same pinned official image was used for each arm. The dedicated host
reported four NVIDIA H200 GPUs, each with 143,771 MiB; the baseline used
`--tensor-parallel-size 4 --max-num-seqs 128`, and finance and math also used
`--max-num-seqs 128`. Temperature was zero, maximum output 512 tokens, and
there were no hidden benchmark retries.

The first baseline attempt exited **before inference** because Docker's default
64 MiB `/dev/shm` could not satisfy vLLM's 160 MiB shared-memory allocation.
The failed container and its host tee, Docker logs and sanitized inspect were
retained; a tested wrapper revision used `--shm-size 2g`, and the TP=4 baseline
was retried successfully before any benchmark case was sent. Each expert passed
its own non-benchmark compatibility smoke. Both arms then used the unchanged
frozen suite. Failure evidence is snapshot `85ce6429`, wrapper revision
`0957e388`, baseline `38cc27bf`, and complete results, joined telemetry and
final container evidence `ac04f7d5` (all `router/v45-proof` artifact tags).
The local full-suite mock and classifier check `12995989` are infrastructure
evidence, not model quality evidence.

The instance was deleted after evidence capture. Independently, it was absent
from the active instance list, its info reported `deleted` with a deletion
timestamp, the exact registered key's deletion endpoint returned 404, and the
local throwaway key was absent. Cleanup evidence is snapshot `df6d2ba5`
(`router/v45-proof/426-h200-cleanup`).

The provider's post-deletion `cost_estimate` was $9.5407991712; this is
**not a posted charge or invoice**, and may exclude lagged costs.
Actual reconciled Shadeform charges and cost per correct task remain unknown.
The previous three #426 Vast attempts showed $6.382 in provisional posted
charges; earlier Shadeform estimates are not invoices. The comparison has no
per-arm billed amounts, and the timing-based ratios above are not GPU prices.
